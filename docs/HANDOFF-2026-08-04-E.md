## 3. 接手第一步

```bash
cd /Users/dwgx/Documents/Project/WindsurfAPI
echo alive
git status --short                             # 期望:干净
git rev-parse master origin/master             # 期望:相同
git describe --tags master                     # 期望:v3.9.17 或 v3.9.17-N-g…(见下)
npm run test:release                           # 期望:3433 / 0(263 个文件)
for s in test/mutations/*.json; do npm run mutate -- "$s"; done   # 期望:六个全绿
```

**不要用 `--exact-match`。** 本文首发时写的是 `git describe --tags --exact-match master`
期望 `v3.9.17`,而 tag 之后又落了文档 commit(`6480f24`、`3d49657`),那条命令必然
`fatal: no tag exactly matches` —— 五步里第三步假报警。带 `-N-g…` 后缀是正常的:说明
master 领先 tag N 个 commit,只要那 N 个不含行为变更就不需要发版。

**两条会立刻绊住你的操作纪律**(本轮各踩了三次):

1. **突变循环启动后就不要碰仓库。** 它每一步都在 `写入 → 跑测试 → git checkout HEAD -- 还原`,
   期间任何别的编辑都会被 guard 6 判脏并中止整轮。要并行干活就去 worktree
2. **commit 前先切分支。** `.githooks/pre-commit` 会拒绝在 master 上 commit,而它拒绝时你那次
   `git add` 已经做了 —— 工作树仍是脏的,紧接着跑突变会被 guard 1 再拒一次

### 5.1 "更正"比新增声明更危险

我判定台账上一轮那句"已加测试钉住"是假的,写成更正落进台账 —— **而守卫一直在**
(`strict-usage-total.test.js`,源码扫描形态,它的失败消息里甚至预先写好了"哪天流式路径真的
记账了就删掉这条")。

怎么错的:grep 提到 `recordAccountSpend` 的测试文件(它命中了),再对命中文件 grep
`stream|cascade`(它又命中了),然后**看着命中行判断那是 usage 算术测试、没打开读**。两次
grep 都指向了正确的文件,我在最后一步用眼扫过去就下了结论。**是全量门禁抓到的,而且在修复
已经提交之后。**

新增声明会被下一轮审;而"我核过了、上一轮那句是假的"会让下一个人**停止怀疑**那个位置。

**动作**:要断言"这个面没有守卫",grep**被守对象的名字**在 `test/` 下的全部命中并**逐个打开
读**。搜索能证明"存在",证明"不存在"需要穷尽,而穷尽必须包括读。另:源码扫描形态的守卫在按
行为搜索时是隐形的。
