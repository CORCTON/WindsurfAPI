# v3.9.19

v3.9.18 给 reasoning digest 的上限加了一道钳,**而那道钳只堵了一半**。这一版堵另一半。

只影响把 `DEVIN_CONNECT_RESCUE_REASONING_MAX_CHARS` 设成 **0 到 1 之间的小数**的部署。没设
或设整数的部署行为字节级不变 —— 但如果你设了 `0.5` 这类值,你拿到的是**完全相反**的效果。

门禁 **3449 pass / 0 fail**(264 个文件;v3.9.18 = 3447,新增 2)。

---

## 缺陷:`MAX_CHARS=0.5` 等于"不设上限",而不是"几乎不引用"

v3.9.18 的清洗是 `Math.min(digestRaw, 32000)`。对 `1e9` 它工作正常。对 `0.5` 它也"正常" ——
`Math.min(0.5, 32000)` **正确地**得到 `0.5`。

问题在下一步。唯一的消费者是 `slice(-n)`,而 `String.prototype.slice` 把参数朝零截断:

```
slice(-0.5)  ===  slice(0)  ===  整个字符串
```

实测(3000 字符 reasoning 的场景放大到 50000 便于看清):

| `MAX_CHARS` | 送出的 digest 长度 | |
|---|---|---|
| `0.5` | **50000** | 全量 —— 上限完全失效 |
| `0.9` | **50000** | 同上 |
| `1` | 1 | 正常 |
| `2000`(默认) | 2000 | 正常 |

**这正是那道钳被加进来要挡的后果。** 一个想把引用调到"几乎没有"的运维,拿到的是把整段
reasoning 塞进每一次救援提示。

修法是 `Math.floor(Math.min(...))`。`Math.floor(0.5) === 0`,而 0 走的是和显式 `0` 相同的
分支:退回不带引用的裸提示 —— 也就是运维想要的那个方向。

## 为什么 v3.9.18 的钳抓不到它

值得单独记一句:**这道钳失败不是因为它写错了,而是因为它对的。** `Math.min` 忠实地保留了
`0.5`,而语义反转发生在它下游的 `slice`。

判据:**钳住取值范围不等于钳住语义。** 给一个数值旋钮加钳之后要接着问 —— 这个数最终被谁
消费,那个消费者对非整数、对 0、对边界值的行为是什么。

## 守卫

2 条断言 + 1 条常驻突变:

- 小于 1 的分数**不得**反转成"无上限"(承重的是第一条断言:修复前它送出全部 5000 字符)
- 大于 1 的分数向下截断而不是抛异常(`100.9` → 100)
- 突变:把 `Math.floor` 摘掉 → **CAUGHT**

突变总数 **67 条 = 62 CAUGHT + 4 条声明的漏网 + 1 条**(v3.9.18 为 66)。
