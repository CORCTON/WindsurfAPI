## 缺陷：一次 thinking-only 救援会吃掉空回复重试的预算（#240）

`streamChatWithEmptyRetry` 里跑着两条投机重发的臂 —— retry-on-empty，和 #238 加的
thinking-only 救援。它们各有自己的上限，**但共用一个计数器**。

救援臂一直有独立的 `rescueAttempt` / `rescueMax`；而空回复臂的判据读的是
`for (let attempt = 0; ; attempt++)` 的 `attempt`。两条臂都靠 `continue` 进入下一轮，于是
每次救援都顺带把 `attempt` 推进一格 —— 而那正是空回复臂的预算。**单向**：空回复重试从不
碰 `rescueAttempt`。

默认值（`RETRY_ON_EMPTY_MAX=2`、`RESCUE_MAX=2`）下实测，两个场景只差"这次请求之前有没有
救援过"：

```
2 次救援，然后一个空回复    3 次上游调用，客户端收到 ""
同一个空回复，前面无救援     2 次上游调用，客户端收到答案
```

一次救援正好吃掉一次空重试，两次吃光。**症状是客户端拿到一个空回复，而它本该被重试治好。**

**总上限刻意不变**：每个客户端请求仍是 `1 + RETRY_ON_EMPTY_MAX + RESCUE_MAX` 次上游调用。
那个上限才是账号保护 —— fable 系的付费 E2E（27/27）证明治不好的重试只会把上游负载翻三倍、
把账号打进 3 小时限流。而它在这次修改**之前就已经够得到**，只在"先空回复"那个顺序上：

| 顺序 | 修改前 | 修改后 |
|---|---|---|
| 全空回复 | 3 | 3 |
| 全 thinking-only | 3 | 3 |
| 先空回复、后 thinking-only | 5 | 5 |
| **先 thinking-only、后空回复** | **3** | **5** |

所以饿死不是"上限太低"，是"上限的花法依赖顺序"。拆开计数器让空回复预算不再依赖顺序，
**不是让它变大**。

判定它是非预期耦合而不是刻意策略，依据在代码本身：**救援臂自带一对计数器**。如果设计本意
是"任何投机重试都从同一个池里喝水"，第二个计数器就是多余的。

退避与日志也改成键在空回复自己的计数上。此前读共享计数器，只在没跑过救援时恰好等于"第几次
空重试"；键在共享计数器上会让一次无关的救援拉长下一次空等待。

报告者 **warelik** 附了 66 天生产日志（158 次 empty-retry、6 次救援、零次可归因的预算耗尽）
并明确把决定权留给维护者 —— 这条边在生产里从未真的踩到，所以它是被测试钉住的，不是被事故
发现的。五条 `RESCUE_MAX` 加固测试（`Infinity` / `1e9` / 非数字 / `0` / 主开关）与 weak-model
否决**全部未经修改**通过。

12 条突变：**11 CAUGHT + 1 条有据可查的漏网**。漏网那条是退避倍数 —— 所有测试都设
`DEVIN_CONNECT_RETRY_ON_EMPTY_MS=0`，两个版本都睡 0ms，倍数不可观测。墙钟断言按本仓库自己的
先例否掉（负载会同时抬高正确与突变两条路径，350ms 与 700ms 之间没有稳定余量）；危害有界且
是观感级，而那个可观测的替代物 —— 日志行报的计数 —— 有断言钉住。

## 工程：`FORCE_COLOR` 让突变工具恒报"你的套件不绿"

`scripts/mutate-verify.mjs` 是台账全部信任的落点（"一条从未失败过的测试等于没有测试"只有在
报 CAUGHT/SURVIVED 的那个东西自己是对的时候才成立）。它此前只从子进程环境里删掉
`NODE_TEST_CONTEXT`。

带 `FORCE_COLOR` 时，node 给测试汇总行套上 SGR 码 —— `\x1b[34mℹ pass 62\x1b[39m` —— 而计数
正则锚在行首行尾，于是**恒得 `pass=0`**，guard 2 以 "baseline is not green" 拒绝启动。套件
其实全绿，坏的是测量。

它**失败在安全侧**（0 计数永远造不出假 SURVIVED），但报错把责任推给套件 —— 与台账第三轮那
四次假 SURVIVED 是同一种伪装：`pass=0` 是"没测量"，不是"没抓到"。

**不是假设**：导出 `FORCE_COLOR=3` 时，`test/mutate-verify-harness.test.js` 自己 **6/10 红**。
换句话说，门禁此前是绿的，只因为环境恰好没设这个变量。修好后带 `FORCE_COLOR=3` 跑全量门禁：
**3405 / 0、EXIT=0**，确认没有别的文件对它敏感。

实测：除 `'0'` 外任何值都会上色，**包括空字符串**；`TERM` / `COLORTERM` 单独不会让管道里的
子进程上色。所以修法是 `delete` 而非覆写。另外在解析前剥一次 ANSI —— 两半**各自单独就够**
（5/9 → 14/0），保留是因为一半治病因（子进程不上色）、一半治形状（解析不依赖颜色从哪来），
注释里如实写明它是冗余而不是合取的两半。
