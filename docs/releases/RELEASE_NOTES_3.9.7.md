四个正在伤害生产的缺陷,加上一批"全绿套件掩盖不了的"测试与文档修正。

本轮最值得说的一条:**四条源码守卫经突变验证放过了它们存在的理由**,而其中一条
的盲区里藏着一个真缺陷 —— 五个传输层错误码仍在把健康账号打下线。守卫看不见的
东西守不住。

## 用户可感知

### 客户端断连吞掉上游已声明的 429 冷却窗口

#224 让 `RATE_LIMITED` 把上游给的真实 reset window 写进账号级冷却,#225 让客户端
断连不再惩罚账号。两条各自都对,但 #225 的 abort 分支排在
`finalizeConnectAccount` 的 else-if 链**最前面**,于是客户端在上游 429 在途时断连,
整条分类都被跳过 —— 包括那个冷却。

实测:上游声明 3h 窗口 → `rateLimitedUntil` 归零,账号立即可再选;5 次断连请求
吸收 5 个上游 429,累计冷却仍是 0。agent 客户端(Claude Code / Codex)中途取消是
常态,所以**每个被取消的轮次都会把一个已限流的账号重新放回池子**,代理继续冲击
上游的速率限制器 —— 而那正是通往数小时硬封禁的路径,也正是 #224 合并时要消除的
失效模式。

修法是把两件事分开:上游声明的**冷却**是关于账号或模型的事实,与我们的客户端
是否还在听无关;而**惩罚**(errorCount 驱逐、re-login、internal 连击)是对"账号
是否有问题"的判断,断连不构成证据。前者无条件执行,后者照旧豁免。

### 真实上游故障被当成客户端断连 → 499 发给根本没断线的客户端

`isAbortError` 的 `/aborted/i` 兜底会命中真实上游故障:`classifyUpstreamError` 把
上游原文放进 `.message`,未知 gRPC code 原样透传,所以一个真的 gRPC `aborted`
trailer(或任何正文含该词的 5xx / 中间盒响应)被读成客户端断连 —— 客户端明明
连着却收到 `499 client_disconnect`,跨账号 failover 被抑制,健康的第二个账号闲置,
冷却与健康信号都不记。一个正文里带 "aborted" 的真 429 同样被整条吞掉。

该兜底本身有存在理由(部分 undici 形态既不带 `name` 也不带 `code`),所以保留但
加前提:错误一旦带任何 code,说明上游已经表态,就不是本地 abort。

### 五个传输层错误码仍在把健康账号打下线

v3.9.6 修过一次这个失效模式,枚举了 `classifyUpstreamError` 能产出的 12 个码。
但**枚举本身有盲区**:socket 级错误码不由那个函数构造 —— 它们带着 `.code` 从
Node 直接过来,原样穿过 connect generator。

实测(seed 一个健康 peer 以排除 `lastAccountExempt` 掩盖):

| 码 | 3 次调用后 |
|---|---|
| `ECONNRESET` | `status='error'` errorCount=3 |
| `ETIMEDOUT` | 同上 |
| `EPIPE` | 同上 |
| `ECONNREFUSED` | 同上 |
| `unavailable`(小写 gRPC status) | 同上 |

也就是说网络抖动或上游丢连接会三个一批地把池子打下线,并写持久化退避。而
`devin-connect.js` 自己的 `RETRYABLE_CODES` 早就把这些列为**可重试的传输条件** ——
拿账号健康去背这个锅,与传输层自己的结论矛盾。

现已并入 `TRANSPORT_FAULT_CODES`(另含 `ENOTFOUND` / `EHOSTUNREACH` /
`ENETUNREACH` / `EAI_AGAIN` / `ECONNABORTED`)。实测 5 次不再驱逐,而对照组
`UNAUTHORIZED` 3 次照旧驱逐。

### 空或畸形的目录响应零确认擦掉 last-known-good

#232 的逐账号确认门存在的意义是:一个退化的上游响应不能缩小账号目录 —— 小于上次
一半的快照要隔离到同一 UID 集合再回来一次。但两种形态从相反方向逃了出去。

**太宽松**:1 个 UID 的快照要隔离两轮,**0 个 UID 的一轮都不要**,而非数组 body
直接走 `applyCloudModels([])` —— 那个调用会**删除**账号快照。实测:已采纳的
101-UID 目录(filter 106/163)在一次空响应后回到 163/163,无确认轮、无重试。
而截断 / 限流 / 鉴权抖动产出的恰恰就是空 body —— 唯一没有门禁的那条路,正是最常
被走到的那条。

零 UID 确实有两种读法,需要相反处理,所以拆开:尚无已采纳快照时它仍然意味着
"本部署没有云端过滤"(既有 fail-open,保持立即生效);已有快照后它只是最大幅度的
缩水,走与其他缩水相同的确认。

**太严格**:缩水但**内容变化**的目录会永久楔住。确认要求 UID 集合完全相同,所以
上游每轮返回的小集合只要差一个 UID 就永远无法自我重复,候选被无限重新隔离,而
更大的陈旧 last-known-good 一直权威 —— 且只在第一轮 arm 过重试,之后没有任何东西
再来纠正它(本项目没有周期性目录刷新)。而这恰恰是最该生效的场景:套餐降级或权限
撤销确实会让目录缩水一半以上。实测:降级后再跑 4 轮同步,代理仍然放行账号已经
失去的模型。

现在隔离有明确上限(3 轮),到顶后采纳最新快照 —— "上游连续多轮都说它很小,只是
每次不同"比"一份此后无人确认过的旧快照"是更好的证据。稳定重复的路径不变,仍然
两轮确认。

### swe-1-7 在 agentic 循环里停滞:声明了工具意图却不发出 tool call(#238,@warelik)

`swe-1-7`(Kimi K2 fine-tune,当前免费档,因此是很多部署的首选 SWE 模型)会间歇性
把整个 turn 花在 reasoning 通道:thinking delta 有内容、content 零、tool call 零、
`finish=stop`。代理原样转发成 `stop_reason=end_turn` + 只有一个 thinking 块,于是
两类客户端各自坏掉 —— 严格客户端(kimi CLI)报 `APIEmptyResponseError` 并 10/10
同样失败,宽容客户端静默丢弃该轮、agent 循环无限停滞(无人值守跑一夜什么都没产出)。
实测:agentic 上下文 **5/20(25%)**,纯文本提问 **5/5(100%)**;其中 60% 的推理
里明确用自然语言声明了工具意图。

三环一链,只修一环没有可观测效果:

1. 上游把整个 turn 花在 reasoning 通道(proto #9),content(#3)零输出,在
   21–174 completion tokens 处停下 —— 不是预算耗尽
2. `isEmptyCompletion` 把 reasoning 计入 `sawContent`,所以空完成重试从不触发
3. 重试历史里那个零长度 assistant turn 被原样转发上游,反过来诱导模型继续产出
   空轮 —— 这就是客户端 10 次重试全部同样失败的原因

修复键在**失效特征**(reasoning-only finish + 有 tools)而不是模型名上:检测到即
剔除历史里的空 assistant turn、追加一句纠正指令重试(≤ `DEVIN_CONNECT_RESCUE_MAX`,
默认 2,设 0 关闭)。作者实测 24/24 恢复,而盲重试只有 20%。已流出的 reasoning 仍
作为 thinking 块保留 —— thinking + tool_use 是合法的 Anthropic 轮次。无 tools 或
重试耗尽时,累积的 reasoning 会被提升为可见 content,所以纯文本提问不再返回空回答。

维护方在合并后又修了两条自查发现的缺陷:

- **提升是搬走而不是复制**。原实现设置 `content` 后仍保留 `reasoning_content`,
  同一段文字返回两遍;三条路径都复现,而 Anthropic 路由上表现为一个 `thinking`
  块加一个内容逐字相同的 `text` 块 —— 正是报告者自己用的 kimi CLI 那条路。流式那半
  修不了(delta 已发出、流不能撤回),记为已知取舍并在调用点写明为何三个替代方案
  都更差。
- **每次 rescue 尝试的输出被拼进同一个答案**。rescue 循环在生成器内部,而累加器在
  它的两个消费者里,消费者只在自己那层重试时重置 —— 实测三次尝试产出
  `"PASS1. PASS2. PASS3. "`。现在生成器发 `attempt_reset` 哨兵,一次 rescue
  **替换**上一次而不是续接。

### 检索端点的 query 通道只认下划线拼写

README 中英把六种作用域信号按 header 拼写列出(`conversation-id` / `session-id`),
紧接着说同名 query 参数保留为降级通道。但下划线→连字符的替换只作用于 **header
名**,query 查的是原始下划线键 —— 于是照文档字面写 `?conversation-id=` 的客户端拿到
404,而且是在专门为"无法设 header 的客户端"准备的那条通道上。现在两种拼写都接受。

## 文档

`.env.example:252` 此前是一条**活跃**的 `DEFAULT_MODEL=claude-4.5-sonnet-thinking`,
而代码默认是 `claude-sonnet-4.6`。照文档 `cp .env.example .env` 的运维是真的把它
设进去了 —— 而在生产默认后端上该名 `mapped:false`,每个不带 model 的请求会被静默
降级成免费 selector `swe-1-6-slow`,**输出与计费都不是他要的模型**。两个 README 的
默认值同样写错。

另外补齐:约 155 个 `src/` 会读的环境变量此前不在 `.env.example`。用 7 种读取模式
重新求了两个方向的差集 —— 反方向("声明了但没人读")确认是**空集**,三个疑似
orphan 全都经间接读取,删任何一个都会砍掉活配置。正方向里多数是校准 tag、调试转储
和已由 Dashboard 面板暴露的内部旋钮,硬塞进运维面文档反而降低信噪比,所以补的是
"运维会去设、不知道会出事"的那批(含 `DROUGHT_RESTRICT_PREMIUM` —— 一个默认开启的
行为门,此前只在 v2.0.58 的 release note 里出现过;`WINDSURFAPI_STRICT_MODEL` ——
标注为陷阱而非兼容开关;`BIND_HOST` —— `HOST` 的别名,且打包版只设它会满足
loopback 兜底判断却不提供 loopback 值),并显式写明另外三类刻意不列及各自去处。

还修了:CUTOVER §1 声称未知模型名会降级到免费 selector(自 strict-model 默认开启
后是 400)、`docs/README.md` 指向一个已移入 git-ignored 目录的死链、CUTOVER 有两个
不同的 §8.8 导致 §8.0.1 的交叉引用无法解析、两条 sticky 注释在断言代码并不提供的
保证(模块头声称模型维度防止跨模型冲突 —— 在生产默认后端上恰恰相反;
`clearCallerBindings` 声称在 session reset / 断连时被调用 —— 它没有生产调用点)。

## 工程:四条源码守卫放过了自己要抓的缺陷

v3.9.6 那轮修掉 5 条假测试后,这轮把**守卫本身**又压了一遍。四条全部经突变验证
失效,其中一条的盲区里就藏着上面那个传输层码缺陷。

| 守卫 | 逃逸口 | 同一突变下 |
|---|---|---|
| `connect-dimension-guard` | `dimension.includes('selector')` 接受**反序**的 `model || selector`(connect 上 `model` 恒真,正是 v3.8.0 CAPACITY 的形状);`[^)]*` 遇嵌套调用截断 —— **未突变源码上就已**只在检查 4 个调用点里的 3 个 | 旧守卫 9/9 全绿 |
| `connect-error-blame` | 正则只读自构造的 `code: 'UPPER'` 字面量,对 Node 透传码结构性盲视,小写 `unavailable` 连字符类都匹配不上 | 旧守卫全绿,报 `emitted.size=12` |
| `handler-route-parity-guard` | `includes('connectErrorToHttp(')` 被一个丢弃返回值的死调用满足 | 旧守卫 10/10 全绿 |
| `dashboard-syntax` 的转义检查 | 只断言四个声明字符串存在;把两个转义函数改成恒等(全仓 207 个调用点一起失效)后仍全绿 | 旧守卫 12/12 全绿 |

修法统一改成"解析一个集合、与另一个集合求差、差非空即失败",而不是存在性检查;
能抽出来跑的就真的跑(Dashboard 的两个转义函数是纯函数,直接从 HTML 抽出执行,
并有元检查钉住抽取拿到的是真实现而非 stub)。新守卫在同一突变下分别抓
1 / 2 / 1 / 11 条。

顺带记两条方法论:

- 本轮我自己写的目录守卫第一版**被自己的注释文本满足**(注释里引用了
  `applyCloudModels([])`,正则就匹配上了)—— 与复核在同族守卫上查出的"注释满足
  断言"是同一个反模式。现在所有结构守卫在读结构前先剥注释。
- Dashboard 行为测试第一版在正则字面量里写了**裸** U+2028/U+2029,直接让整个源文件
  解析失败 —— 而 `escJsAttr` 自己的注释恰好警告过这一点。**读过某条约束不等于会
  遵守它。**

### 一条时间竞态假测试

`test/rate-limit.test.js:120` 断言 `retry_after_ms` 精确等于 1632000。它在 v3.9.5
的发布 commit 上挂掉了 CI(actual 1631999),另有一次在 45 连跑的第 27 次复现。

走到的那条分支取 `max(各事件 cooldownMs)`,而每个都来自 `until - Date.now()`;
传给它的是**本地化**的代理消息,解析不出精确常量 —— 所以候选里根本没有 1632000,
两次读表之间被调度器插一下就是 1631999。

它还同时耦合了"走哪条分支":注入 4.5 秒延迟后 8 秒窗口被剪掉,另一条分支回答约
1622996ms —— 而原断言把它当成"大约 1632000"照样通过,**测试在走错代码路径时仍然
全绿**。现在两个维度都钉:数值用双侧容差,分支用其消息特征显式断言。

**测试 3119 → 3179**,全量绿(`npm run test:release`,逐文件进程隔离)。
