# v3.9.18

上游有时把一整轮花在"想"上 —— reasoning 有内容、工具调用零个、`finish=stop`。对 agentic
客户端来说这就是**光想不做**,自主循环停在那里等一个永远不来的工具调用。

v3.9.16 起代理已经会在这种轮次后补一条纠正提示("别想了,现在把工具调用发出来")。**问题是
那条提示不带上下文,模型只能从零重想。** 这个版本让它带上模型自己刚才想到哪。

来自 [PR #241](https://github.com/dwgx/WindsurfAPI/pull/241)(warelik),#238 的第二层。

门禁 **3447 pass / 0 fail**(264 个文件;v3.9.17 = 3433,新增 14)。

## 用户可感知:救援提示引用上一次失败尝试的 reasoning 尾巴

失败那一轮的 reasoning 会被截取尾部(默认 2000 字符)包进提示:

```
Your previous reasoning ended with: """…上一轮 reasoning 的最后 2000 字符…"""
Stop reasoning. Emit the tool call markup now.
```

**取尾而不是取头**,因为模型最后的意图在末尾 —— 它刚要决定调哪个工具的地方。

只在**请求带 tools** 时触发。没有工具的纯聊天轮次以 reasoning 或文本收尾是正常的,不救援。

默认开,零配置。

### 旋钮

```bash
# 保留多少尾部 reasoning 字符。默认 2000;0 = 退回不带引用的纯提示
DEVIN_CONNECT_RESCUE_REASONING_MAX_CHARS=2000

# 救援次数上限。默认 2,硬上限 5
DEVIN_CONNECT_RESCUE_MAX=2
```

**留空等于 0**(即关掉),因为 `Number('') === 0`。想回到默认值就把整行注释掉,不要留空。
这一点对本文件里的另外三个 `DEVIN_CONNECT_RETRY_*` / `RESCUE_MAX` 旋钮同样成立。

## 为什么恢复要做在代理这边

证据是 wire 级的,不是推断:

- 2026-07-28 的 trajectory 第 8 步(上游 → 代理):13 个 `reasoning` delta,然后 `finish`,
  content **零**。而同一账号、同一模型的第 3、5 步正常发出工具调用 —— **账号有这个能力,
  只是有时不用**
- 同账号同模型的 A/B 探针:带 tools 时可复现纯思考轮次;`tool_choice: required` **不改变
  结果**。所以缺口在上游生成侧,代理这边只能做恢复
- #238 的 9 组 wire 验证确认:这个上游**接受**但**不消费** `thinking` 块。所以提示是作为
  普通 user 文本注入的 —— 那是这个账号唯一稳定会照做的通道

## 工程

### 一次救援恰好一条新提示

原来每次救援从**已经变长的**消息列表重建,而旧提示是 `role:'user'`、过滤器只丢空 assistant
轮,所以旧提示全部留下。带上 reasoning 引用之后这件事从"看不见"变成"要紧":

实测(每轮 3000 字符 reasoning、`RESCUE_MAX=5`;计的是每次上游调用里**救援提示占的字符数**,
两列同一个探针):

| 第 N 次上游调用 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 修复前 | 0 | 2089 | 4178 | 6267 | 8356 | **10445** |
| 修复后 | 0 | 2089 | 2089 | 2089 | 2089 | **2089** |

比字节数更要紧的是语义:**第 3 次调用起模型会同时看到两条都写着"你上次想到"的消息,各引用
不同一次尝试** —— 正好和这个设计想达到的效果相反。现在每次救援从未经修改的原始请求重建。

### digest 的上限

`DEVIN_CONNECT_RESCUE_REASONING_MAX_CHARS` 的清洗用 `Number.isFinite`,而它**放 `1e9` 过去**。
实测:50000 字符 reasoning + `1e9` → 提示 **50089 字节**,该请求的每一次救援都送这么大。

已加硬上限 **32000**。同一个函数里的 `DEVIN_CONNECT_RESCUE_MAX` 早就因为同一个洞加过钳
(`1e9` 会让请求挂几个小时的上游调用,实测),digest 这条当时没跟上。

32000 是判断,**不是实测的上游 body 上限** —— 那个数从来没探过,源码注释里写明了。

### protobuf 字段 0

`encodeAssistantToolCall` 的 reasoning tag 在 replay 关闭时算出来是 0,而 `writeStringField(0, …)`
会编出 `makeTag(0,2)`,字段 0 在 protobuf 里是保留的。三个调用点都在外面守住了,所以当前
不可达 —— 但编码器现在自己拒绝它,不再依赖调用方。

## 守卫

新增 14 条断言,其中值得单说的三条形态:

- **一条前置断言**:`assert.equal(callCount, 4)`。没有它,后面每条"提示只有一条"的断言都会在
  **压根没发生救援**的运行上恒真
- **显式断言陈旧引用不在场**,而不只是断言"有一条提示"
- **字节长度同一性**:tag-0 的 reasoning 被丢掉后,输出必须与无 reasoning 的帧逐字节等长

突变验证 **66 条 = 62 CAUGHT + 4 条声明的漏网**(v3.9.17 为 60 条)。新增 6 条里有一条是
把"提示累积"那个缺陷**原样打回**——让它有常驻突变守着,而不是只靠一条断言。
