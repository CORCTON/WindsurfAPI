# v3.9.6

一轮代码质量复核的产出。修掉三个仍在**误把健康账号打下线**的上游错误码,并修正
五条自己写的假测试 —— 其中两条被证实完全测不到它们声称守护的东西。

升级无需改配置。

---

## 用户可感知

### 三个上游错误码不再把健康账号打下线

v3.9.2 修过一次这个失效模式:新增的 `STREAM_TRUNCATED` 落进
`finalizeConnectAccount` 末尾的兜底 `else reportError`,于是**传输层**故障被记进账号
错误预算,攒够就把账号翻成 `status='error'` 并写持久化退避。

那次只修了**那一个码**。这轮枚举了 `classifyUpstreamError` 能产出的全部 12 个码,
发现还有三个在下面:

| 码 | 实际含义 | 实测 |
|---|---|---|
| `TIMEOUT` | idle 超时。本文件自己的注释称其为"往往是可重试的上游停顿" | 3 次 → `status='error'` |
| `DEADLINE_EXCEEDED` | 绝对墙钟上限。上游挂住了,账号没问题 | 3 次 → `status='error'` |
| `NO_TOKEN` | 压根没配 session token —— **配置**故障 | 3 次 → `status='error'` |

`NO_TOKEN` 那条尤其糟:配置错了却惩罚账号健康,而且它会在**每个**请求上重复触发 ——
配置修好之前账号池会被一个个打下线。

三者现在记 health-window 事件(真病的账号照旧被选择逻辑降权)但不走 errorCount 驱逐,
与既有的 `CONTENT_BLOCKED` / `UPSTREAM_ERROR` / `STREAM_TRUNCATED` 同档。
新增 `transport_fault` 计数器:它的尖峰意味着上游在停顿或部署配错了,而不是账号池在死。

## 工程

### 给静默兜底加了结构守卫

这是**同一个结构原因第二次发作**,所以这次不只修码,还堵住了模式本身。

那条分类以裸 `else reportError(apiKey)` 收尾 —— 任何没人想到的错误码都被静默当成账号
故障。行为测试抓不到**下一个**,因为那段代码还没写。

新守卫读两份源码:当 `devin-connect.js` 能产出的码在 `finalizeConnectAccount` 里没有
明确归属时**直接构建失败**,并在错误信息里写明该怎么决策(真账号故障留在兜底,其余
进 `TRANSPORT_FAULT_CODES` 或自己的分支)。

### 五条假测试,共同病因是"源码 grep 冒充行为守卫"

复核唯一跑成功的那一面审的是**测试本身**,五条全部经独立突变验证成立 ——
其中四条是最近几个版本刚写的守卫:

1. **DELETE 快乐路径从未执行。** 断言包在
   `if (res.statusCode === 200) {...} else { assert 404 }` 里,而
   `WINDSURFAPI_SINGLE_TENANT_CACHE` 在 `chat.js:850` 是 **import 期冻结的 const**,
   运行时设它无效 → 永远走 404 支。实测:把 DELETE 端点整个改成
   `if (true) return responseNotFound(...)`,该套件 **11/11 全绿**。
   **条件断言只能证明它恰好走到的那一支。**
2. **header 身份通道只有 `assert.match(serverSrc, /x-response-/)` 守着。**
   实测:去掉 header 名的下划线→连字符转换后,六个信号里**四个全部 404**,
   而 35 个检索测试全绿。现改为在 route 套件里**真的发**六个 header 走 HTTP。
3. **作用域词汇检查可被注释满足** —— `includes("'conversation_id'")`,而
   `server.js:715` 的注释里就有该字样。改为解析 `caller-key.js` 真实的 POST 侧词汇,
   与 router 的 `pick()` 列表求差集。
4. **单条上限测试证明不了单条上限。** 它在**空 store** 上写一条 50MB,而空 store 里
   全局 LRU 无可回收,断言成立的原因与上限无关。补"已有邻居租户"场景 —— 实测取消上限后
   5 租户 + 一次 2MB 写入达 **2.6 倍超额**。
5. **四条恒真断言** —— `doesNotMatch(html, /pageSize=1000/)`,而 `index.html` 从不用
   query 串形态写 pageSize。更糟:它们要防的"1000 行默认加载"**已经存在**
   (`pageSize: '1000'`,CSV 导出路径),而它们一直绿着。

修完后,那两个此前**存活**的突变现在分别抓 4 条和 3 条。

**教训**:源码 grep 分不清"功能可用"和"字符串还在"。它只适合守**结构性不变量**
(如"新增内部路由必须消费某信号"),不能替代行为验证。

### 复核中的一次假警,以及为什么值得记

复核期间我曾报告"#232 的逐账号目录隔离失效",给出了实测输出。**那是误报** ——
漏了 `4e805562` 的两轮确认机制:首次同步没有 last-known-good,基线取静态目录数,
所以小目录需第二轮相同快照才采纳,而探测脚本只调了一次。补上确认轮后隔离完全正确。

推翻自己的假警比发现它花的时间更长。这正是"报告者必须被独立验证"这条纪律的意义 ——
**包括报告者是自己的时候。**

复核另外四面(伪造信号的其他实例 / 内存与生命周期 / 四协议一致性 / #232 新代码
安全面)未发现新的生产缺陷:合成 usage 不进 per-account 计费(缓存命中路径 apiKey 传
null 且从不调 `recordTokenUsage`);500 轮账号增删后无漂移;2000 次内容各异的小目录
不会让 pending 无界增长、也不注入模型行;截断轮次不污染 sticky / session
(两者都在 `if (r.kind === 'ok')` 内)。

**测试 3112 → 3119**,全量绿(`npm run test:release`,逐文件进程隔离)。
