# v3.9.17

一个写法差异让 GLM-5.2 拿到了它会忽略的工具方言 —— 症状是工具调用永远不发出来，客户端一直等。

门禁 **3433 pass / 0 fail**（263 个文件；v3.9.16 = 3431，新增 2）。

---

## 缺陷：裸写 `glm-5-2` 的工具方言是错的

`pickToolDialect` 对 GLM-5.2 匹配三种字面写法：`glm-5.2`、`glm-5.2-*`、`glm-5-2-*`。

**裸的 `glm-5-2` 三条都不中** —— 它不等于 `glm-5.2`，又因为没有尾部破折号，两条前缀判断都不
成立 —— 于是落到 `glm47`。

而 `glm47` 正是这个模型**会忽略**的方言，这一点就写在同一段注释里（v2.0.72 探测）：它收到那套
XML markup 之后改用纯文本回答。

**后果不是报错。** 模型答得好好的，只是**不发出任何 tool call**，于是客户端一直等一个永远不
会来的工具调用。这是最难诊断的失败形态之一 —— 没有错误码、没有异常日志，只有停住。

`resolveConnectSelector` 把 `glm-5.2` 和 `glm-5-2` 映射到同一个上游 selector，所以客户端发哪
种写法都合法，而且真的会发（#236 报的就是 `glm-5-2-none`）。**其余每一种写法本来都正确，这正
是它一直藏着的原因。**

修法是比较前先把点 collapse 成破折号。

## 守卫

两条，第二条是必要的那条：

1. 八种写法（点/破折号 × 裸/带后缀 × 大小写）全部必须是 `gpt_native`
2. **反方向**：`glm-4.7` / `glm-4-7` / `glm-5` / `glm-5.1` / `glm-5-1` 必须仍然是 `glm47`

没有第二条，一个 `startsWith('glm-5')` 式的修法会把 `glm-5` 和 `glm-5.1` 一起吞掉、且第一条
照样全绿。实测：把旧的三条字面匹配打回去，第一条守卫立刻红。
